# Seed Architecture Plan

## 1. Directory Structure

```
src/db/seed/
  index.ts                    # Entry point — orchestrates all seed groups in dependency order
  utils.ts                    # Shared helpers (UUID generation, connection, truncation)
  truncate.ts                 # Truncation runner — drops all rows in reverse FK order
  00-root-master.ts           # countries, religion, grades, costCenters, projects
  01-companies.ts             # companies
  02-company-children.ts      # departments, workingZones, trainingTypes, trainings, trainingSchedules, warningGrades
  03-allowances-warnings.ts   # allowances, warnings (depend on countries + companies + warningGrades)
  04-positions.ts             # positions (depends on departments)
  05-employees.ts             # employees (depends on companies + departments + positions)
  06-employee-details.ts      # employeeAddresses, employeeContracts, employeeContractAdvisors,
                              # employeeLeaveAdvisors, employeeMcus, employeeProjects,
                              # employeeTrainings, employeeWarnings, employeeWorkZones
```

**Rationale:** Domain modules, not a single file. Each file corresponds to a dependency layer — a module only imports schemas it seeds, and the orchestrator runs them in order. This makes it easy to add/remove seed groups as tables evolve and to seed only a subset during development.

## 2. Table Truncation Order

Truncation must go **children before parents** (reverse of creation order). Each truncation batch is safe to run as a single `DELETE FROM <table>` or `TRUNCATE <table> CASCADE` — but `CASCADE` is risky if `onDelete: 'restrict'` is enforced; plain `TRUNCATE` with sequential batches guarantees FK compliance.

| Order | Group | Tables | FK Dependencies (why they must go first) |
|-------|-------|--------|------------------------------------------|
| 1 | Employee details | `employeeAddresses`, `employeeContracts`, `employeeContractAdvisors`, `employeeLeaveAdvisors`, `employeeMcus`, `employeeProjects`, `employeeTrainings`, `employeeWarnings`, `employeeWorkZones` | All FK to `employees`; `employeeProjects` also FK to `projects`; `employeeWorkZones` also FK to `workingZones` |
| 2 | Employees | `employees` | FK to `companies`, `departments`, `positions` |
| 3 | Warnings | `warnings` | FK to `companies`, `warningGrades` |
| 4 | Allowances | `allowances` | FK to `companies`, `countries` |
| 5 | Positions | `positions` | FK to `departments` |
| 6 | Company children | `departments`, `workingZones`, `trainingTypes`, `trainings`, `trainingSchedules`, `warningGrades` | All FK to `companies` |
| 7 | Companies | `companies` | FK to `countries` |
| 8 | Root master | `countries`, `religion`, `grades`, `costCenters`, `projects` | No FK dependencies (leaf nodes) |

### Truncation strategy

Use `TRUNCATE <table1>, <table2>, ... RESTART IDENTITY CASCADE` per group. `RESTART IDENTITY` resets sequences (relevant if any serial types used). `CASCADE` is safe here because we already ordered groups and there are no cross-group references at this point. If `onDelete: 'restrict'` causes issues, fall back to batch `DELETE` within a transaction.

## 3. Seed File Organization

```
src/db/seed/
├── index.ts              # Orchestrator — calls truncate(), then each domain module
├── utils.ts              # db instance, seed helpers
├── truncate.ts           # truncate function
├── 00-root-master.ts     # countries, religion, grades, costCenters, projects
├── 01-companies.ts       # companies
├── 02-company-children.ts# departments, workingZones, trainingTypes, trainings, trainingSchedules, warningGrades
├── 03-allowances-warnings.ts  # allowances, warnings
├── 04-positions.ts       # positions
├── 05-employees.ts       # employees
└── 06-employee-details.ts    # employeeAddresses, employeeContracts, employeeContractAdvisors, employeeLeaveAdvisors, employeeMcus, employeeProjects, employeeTrainings, employeeWarnings, employeeWorkZones
```

### Module contract

Each `0N-*.ts` module exports a single async function:

```ts
export async function seed(db: ReturnType<typeof initDatabase>): Promise<void>
```

The orchestrator calls them sequentially. Each module internally uses Drizzle `db.insert(table).values(...)` wrapped in a transaction.

### Shared helpers (`utils.ts`)

- `db` — reuses `initDatabase` from `src/db/index.ts`
- `seedId()` — returns `randomUUIDv7()` for consistent-length UUIDv7 PKs, or lets the DB default generate
- `defaultColumns(createdBy?: string)` — returns `{ stsActive: true, createdAt: new Date(), createdBy: createdBy ?? 'seed', updatedAt: new Date(), updatedBy: createdBy ?? 'seed', deletedAt: null }`

## 4. Dependencies Between Seed Groups

| Seed group | Requires (must be seeded first) | Required by (must seed this first) |
|------------|--------------------------------|-----------------------------------|
| `00-root-master` | (none) | `01-companies`, `06-employee-details` (employeeProjects → projects) |
| `01-companies` | `00-root-master` (countries) | `02-company-children`, `03-allowances-warnings`, `05-employees` |
| `02-company-children` | `01-companies` | `03-allowances-warnings` (warningGrades), `04-positions` (departments), `05-employees` (departments), `06-employee-details` (workingZones) |
| `03-allowances-warnings` | `00-root-master` (countries) + `01-companies` + `02-company-children` (warningGrades) | (none) |
| `04-positions` | `02-company-children` (departments) | `05-employees` |
| `05-employees` | `01-companies` + `02-company-children` (departments) + `04-positions` | `06-employee-details` |
| `06-employee-details` | `00-root-master` (projects) + `02-company-children` (workingZones) + `05-employees` | (none) |

Key insight: the strict ordering means modules cannot be parallelized — each group must wait for its dependencies.

## 5. How to Run

### Package.json script

```json
{
  "scripts": {
    "seed": "bun run src/db/seed/index.ts"
  }
}
```

### Seed runner (`index.ts`)

```ts
import { initDatabase } from "../index";
import { truncateAll } from "./truncate";
import { seedRootMaster } from "./00-root-master";
import { seedCompanies } from "./01-companies";
import { seedCompanyChildren } from "./02-company-children";
import { seedAllowancesWarnings } from "./03-allowances-warnings";
import { seedPositions } from "./04-positions";
import { seedEmployees } from "./05-employees";
import { seedEmployeeDetails } from "./06-employee-details";

async function main() {
  const db = initDatabase();

  console.log("[seed] Truncating existing data...");
  await truncateAll(db);

  console.log("[seed] Root master data...");
  await seedRootMaster(db);
  console.log("[seed] Companies...");
  await seedCompanies(db);
  console.log("[seed] Company children...");
  await seedCompanyChildren(db);
  console.log("[seed] Allowances and warnings...");
  await seedAllowancesWarnings(db);
  console.log("[seed] Positions...");
  await seedPositions(db);
  console.log("[seed] Employees...");
  await seedEmployees(db);
  console.log("[seed] Employee details...");
  await seedEmployeeDetails(db);

  console.log("[seed] Done.");
}

await main();
```

### Execution

```sh
DATABASE_URL=postgres://... bun run seed
```

The seed script reads `DATABASE_URL` from the environment, same as the app and migrations.

## 6. Recommended Data Volume

### Master tables (3–5 rows each)

| Table | Rows | Notes |
|-------|------|-------|
| `countries` | 3 | e.g. Indonesia, Singapore, Malaysia |
| `religion` | 4 | e.g. Islam, Protestant, Catholic, Hindu |
| `grades` | 3 | e.g. I, II, III |
| `costCenters` | 3 | e.g. HQ-IT, HQ-FIN, OPS-MFG |
| `projects` | 3 | e.g. PROJ-ALPHA, PROJ-BETA, PROJ-GAMMA |
| `companies` | 3 | One GROUP, one CLIENT, one SUBCON |
| `departments` | 3–5 | Per company, e.g. HR, Finance, IT, Operations |
| `positions` | 3–5 | Per department, mix of HOD and non-HOD |
| `workingZones` | 3 | Per company, e.g. Zone-A, Zone-B, Zone-C |
| `trainingTypes` | 3 | Per company, e.g. Safety, Technical, Soft skill |
| `trainings` | 3 | Per company, e.g. Fire Drill, Welding 101 |
| `trainingSchedules` | 3 | Per company, dates spread across the year |
| `warningGrades` | 3 | Per company, e.g. SP1 (ringan), SP2 (sedang), SP3 (berat) |
| `warnings` | 3 | Per company, referencing warning grades |
| `allowances` | 3–5 | Per company, with nominal values and currency |

### Employee sub-tables (2–3 rows each)

| Table | Rows | Notes |
|-------|------|-------|
| `employees` | 2–3 | Mix of STAFF/WORKER, PERMANENT/CONTRACT; one should have a supervisorId referencing another employee |
| `employeeAddresses` | 2–3 | Per employee, different address types |
| `employeeContracts` | 2 | Per employee, at least one active and one expired |
| `employeeContractAdvisors` | 2 | Per employee, with order 1 and 2 |
| `employeeLeaveAdvisors` | 2 | Per employee, with order 1 and 2 |
| `employeeMcus` | 2 | Per employee, one PASS one FAILED |
| `employeeProjects` | 2–3 | Each employee assigned to 1–2 projects |
| `employeeTrainings` | 2 | Per employee, mixed statuses |
| `employeeWarnings` | 1–2 | Per employee, PERMANENT or TEMPORARY |
| `employeeWorkZones` | 2 | Per employee, assigned zones |

### Total seed volume

Approximately **60–85 rows** total — enough for manual testing and integration test fixtures without being unwieldy.
