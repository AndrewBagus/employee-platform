# Review: GET /companies Endpoint

## Blocker

None found. The implementation is structurally sound and should function correctly when all dependencies are installed and `DATABASE_URL` is set.

## Warnings

### [WARN] Missing error handling in controller

`company.controller.ts:13` — `findAll()` has no try/catch. If `this.service.findAll()` throws (DB connection lost, query timeout, schema mismatch), the rejection propagates unhandled. Hono's default error middleware catches it and returns a 500, but the response shape will be Hono's generic HTML/JSON, not the project's `{ success, data, message }` envelope.

**Recommendation:** Add a try/catch in the handler:

```ts
findAll() {
  return async (c: Context) => {
    try {
      const companies = await this.service.findAll();
      return c.json({
        success: true,
        data: companies,
        message: "Companies retrieved successfully",
      });
    } catch (error) {
      return c.json(
        { success: false, data: null, message: "Failed to retrieve companies" },
        500,
      );
    }
  };
}
```

Alternatively, wire a global Hono error-handling middleware that normalizes all errors to the same envelope.

### [WARN] No runtime validation between DB rows and DTO shape

`company.repository.ts:22` — `rows as CompanyResponseDto[]` is a compile-only type assertion. If a future schema migration adds/drops/renames a column, or if the drizzle `casing` config ever diverges from the drizzle-kit config, the runtime data may have keys that don't match the DTO (e.g., `country_id` vs `countryId`). There is no validation layer (zod, class-validator, etc.) between the database and the API response.

**Recommendation:** Consider adding a validation library (zod is a lightweight option) to parse/validate query results against a known schema. At minimum, document the assumption that `casing: "snake_case"` ensures camelCase keys in query results.

### [WARN] tsconfig missing `target`, `module`, `moduleResolution`

`tsconfig.json` does not set `target`, `module`, or `moduleResolution`. The TypeScript defaults for these depend on the TS version and may produce unexpected strictness or resolution behavior:

- **`target`**: defaults to ES5 in some TS 5.x versions. With `experimentalDecorators: true`, a target below ES5 breaks decorator support entirely. Newer TS versions default to ES2022, which is fine. The project is at the mercy of whichever TS version `bun`/`bunx tsc` installs.
- **`moduleResolution`**: defaults to `classic` for non-`node` module settings, which does not resolve packages from `node_modules` correctly. With `types: ["bun"]` and bun's runtime, this likely works, but for standalone `tsc --noEmit` type checking it could produce false-positive "cannot find module" errors.

**Recommendation:** Add explicit settings:

```json
{
  "compilerOptions": {
    "target": "ES2022",
    "module": "ESNext",
    "moduleResolution": "bundler",
    ...
  }
}
```

The `bundler` resolution is appropriate for a Bun project and matches how Bun resolves imports at runtime.

## Notes

### [NOTE] Controller uses a factory method pattern

`company.controller.ts:12` — `findAll()` returns a closure (`() => async (c: Context) => { ... }`). This is valid but each call to `controller.findAll()` creates a new function object. Since `routes.ts` calls it once at module load time, the overhead is negligible. Consider using a class property arrow function for consistency if other controllers use that style:

```ts
findAll = async (c: Context) => { ... }
```

Then the route would be `app.get("/companies", controller.findAll)` (no invocation parens).

### [NOTE] `reflect-metadata` imported in two places

Both `src/index.ts:1` and `src/di/container.ts:1` import `"reflect-metadata"`. Node/Bun module cache makes this harmless (the module executes once), but the import in `container.ts` is redundant when `index.ts` already imports it first. Consider removing it from `container.ts` to make the sole entry-point import the canonical one.

### [NOTE] `DATABASE_URL!` non-null assertion

`container.ts:15` — `process.env.DATABASE_URL!` causes a `TypeError` at runtime if the env var is missing. Consider an explicit guard:

```ts
const databaseUrl = process.env.DATABASE_URL;
if (!databaseUrl) throw new Error("DATABASE_URL environment variable is required");
```

### [NOTE] `casing` consistency confirmed

Both `drizzle.config.ts` and `container.ts` use `casing: "snake_case"`. This is correct — drizzle-kit generates snake_case migration SQL, and the runtime ORM transforms camelCase schema property names to/from snake_case columns. Query results will have camelCase keys matching `CompanyResponseDto`.

Drizzle ORM v0.45.2 (confirmed from `package.json`) supports the `casing` option (introduced in v0.33.0). ✓

### [NOTE] CompanyController is bound with `toSelf()` without an interface binding

`container.ts:25` — `container.bind(CompanyController).toSelf()`. This is correct and intentional — the controller is used as a concrete class (`container.get(CompanyController)`) and not through an interface. No issues.

### [NOTE] Inversify v8 compatibility

Inversify v8.1.0 uses the legacy `experimentalDecorators` / `emitDecoratorMetadata` pattern that matches the tsconfig settings. All classes are decorated with `@injectable()` and all constructor-injected parameters have `@inject(TYPES.XXX)`. ✓
